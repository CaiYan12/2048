# T41 · 窄视口横向溢出：棋盘 + 页边距把 320 视口撑到 328

**来源**：T37 的独立审查（2026-10-09）复核实现者的一条发现后**证实的部分**，用基线探针钉死的事实票。
**Blocked by**: 无。**GitHub**: #43。

## 现象（审查者实测，非自述）

- 移动端视口 **320px**、开着一局时，页面 `scrollWidth = 328 > clientWidth = 320`——**棋盘本身
  只有 312 < 320**，把它们撑出去的是**棋盘 + 页边距**。
- 有横向溢出时移动端 Chromium 缩放适配，`window.innerWidth = 328 ≠ 100vw = 320`（visualViewport
  同步 328，scale ≈ 0.976）。
- 间歇出现：审查者六次尝试**只复现出 8px 的带（328/320）**，未复现实现者最初报的 444/320
  （124px 带）；这是加载/缩放竞态，不是稳定几何。
- **「看得见点不着」不成立**：对那条带上的点做 `elementFromPoint`，命中全是 `settings-scrim`——
  那条带就是遮罩，点它关抽屉。规格决策 21 担心的陷阱不会发生。
- **不是设置抽屉引入的**：在基线 `f24b54d` 上、抽屉闭合（DOM 里根本没有抽屉）时同样出现
  328/320。抽屉只是继承者——它的 `width: min(22rem, 100vw)` 在缩放态下钉在 328 的视觉右缘、
  只宽 320，左缘差 8px。

## 交付范围

把「窄视口横向溢出」修掉，或在核实后明确接受并记录。**方向开放**，候选：

1. 棋盘/外壳的宽度读数问题（某处用了 `innerWidth` 口径而布局按 `clientWidth` 落，或相反）；
2. 页面左右边距在 320 档没有让位；
3. 若查明是平台缩放行为且无实害，把结论写进 `e2e-debt.md` 并关闭本票。

## 验收标准

- [ ] 320 与 360 档视口、开着一局（棋盘内容最宽的档）时，`document.scrollingElement` 的
      `scrollWidth == clientWidth`；或报告明确论证了做不到与为什么。
- [ ] 若修了：`window.innerWidth` 与 `100vw` 在移动端视口一致（或差异被证明无观感后果），
      且设置抽屉在**运行态窄屏**（不是开局界面）下贴满视觉右缘。
- [ ] 若接受：结论与证据进 `.codex/memories/e2e-debt.md`，本票以「已核实、接受」关闭。
- [ ] 既有契约不为它改绿；涉及棋盘尺寸的改动要跑 `game.spec.ts` 与 `settings-drawer.spec.ts`。
